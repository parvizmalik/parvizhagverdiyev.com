server log
$ start service
Failed to bind listener socket to <server>:<port P>
Got error: '98, Address already in use'

Here's the puzzle

  1. Two routers, A and B, send messages to one port on my server.
  2. The service behind that port stopped. Router A's connection dropped. Router B's stayed alive.
  3. I started the service again and got "Address already in use." I checked: nothing was listening on that port.
  4. Then I restarted one process. Now the same IP and the same port served both routers. No error.

A minute ago the port was "in use". Now it happily serves two routers at once. How?

Take a guess before you scroll. The full answer is in Part 6.

1The short version

The port wasn't taken by some stranger. It was held by my own server, through Router B's connection that never got closed.

What happened, in three lines

  1. The service stopped. The listener closed, Router A's connection closed, but Router B's connection was left open.
  2. That leftover connection kept its claim on the port, so every new start got error 98.
  3. Restarting the whole process made Linux close everything. The port was free, and both routers came back.
Picture a building The entrance is the port. The doorkeeper is the listener. The visitors are connections.
  • The doorkeeper went home. Visitor A left. Visitor B stayed inside.
  • House rule: a new doorkeeper can't start while a visitor let in by the old one is still inside.
  • So the new doorkeeper got turned away, again and again.
  • The restart cleared the whole building. New doorkeeper in, both visitors back.

Linux cleans up after processes, not after services.

When a service stops, closing its connections is the platform's job. If the platform forgets one, Linux won't step in, because the process is still running and still "owns" that connection. Think of the process as a shopping mall and the service as one shop: close the shop, and the mall's front desk keeps working.

For the technically curious
  • Diameter (RFC 6733) is a signaling protocol used in telecom networks, for example to send usage records between systems.
  • SCTP is a transport protocol like TCP. It sends small heartbeats to check the other side is alive. Diameter adds its own keep-alive, called watchdog messages.
  • Multi-homing: each router reaches the server over two network paths. If one fails, the same connection moves to the other.
  • On Linux, the listener and each connection are separate sockets. Remember this one. It's the key to Part 6.

3The problem

The service was found stopped. Starting it again failed with this:

server log
Failed to bind1 listener socket2 to <server>:<port P>3
Got error: '98, Address already in use'4
  1. 1bind: claim the port, so you can listen on it.
  2. 2listener socket: the "open entrance" the routers connect to.
  3. 3server:port P: which address and port it tried to claim.
  4. 4error 98: Linux says something already holds this address and port.

In short: the service said "I want port P", and Linux said "No, it's taken."

It wasn't a config mistake

A newer version of the service failed the exact same way. When every version fails identically, the problem isn't inside the service. Something outside it was holding the port.

Here's the weird part

The usual reason for error 98 is boring: another program already listens on that port. So I checked who was listening on port P.

What Linux said

Port P is already in use

vs

What I saw

Nobody is listening on port P

↓
So who is holding the port?

"Nothing is listening" only rules out listeners. A port can also be held by an open connection. That's exactly what was going on.

For the technically curious
  • Error 98 is EADDRINUSE. It comes from bind(), the system call a program uses to claim an address and port.
  • On bind(), Linux checks its table of open sockets. If any socket already holds the same address and port, and the program didn't ask for permission to share it, Linux refuses.

5Why it happened

When a service stops, the platform should clean up everything it used. One cleanup step was missed. Everything else followed from that.

What should happen

  1. ✓Remove the message handler
  2. ✓Close the SCTP listener
  3. ✓Close Router A's connection
  4. ✓Close Router B's connection

What actually happened

  1. ✓Remove the message handler
  2. ✓Close the SCTP listener
  3. ✓Close Router A's connection
  4. ✗Router B's connection kept open by the Diameter stack

From the outside I can't see why one connection closed and the other didn't. The vendor's own documentation lists this case: a service with an open SCTP connection can't always be stopped cleanly.

What followed, in order

  1. Router B's connection still holds port P.A connection that came in through port P stays on port P while it's open.
  2. The service starts and asks Linux for port P.Linux finds Router B's connection still there and refuses: error 98.
  3. Every new start fails the same way.A new version doesn't help. The blocker isn't in the service.
  4. The Diameter stack retries its SCTP listener every 10 seconds.Same leftover connection, same error 98.
  5. Router B keeps sending Diameter messages.Its connection looks healthy, most likely because the Diameter stack still answers its watchdog checks. Every message gets rejected.
  6. Router A can't get back in.Its connection closed, and there's no open entrance to call.

Why Linux didn't clean it up

  1. The service stopped, but Linux doesn't know services exist.
  2. The process was still running.
  3. To Linux, the process still owned Router B's connection.
  4. So Linux kept the connection, and with it, the claim on port P.

6The puzzle: one port, many connections

Back to the question from the top:

If port P was "in use" and the service couldn't get it, how could the same port serve two routers right after the restart?

The port was never blocked from serving connections. It was blocked from getting a new owner.

Three small ideas make this click.

Idea 1: Linux tells connections apart by four values

Not by the port alone. After the fix, the two connections looked like this:

ConnectionLocal addressLocal portRemote addressRemote port
Router A192.0.2.10P198.51.100.1117921
Router B192.0.2.10P198.51.100.2117153
  1. Same local side: same server, same port P.
  2. Different remote side: different router, different port.
  3. So these are two different connections sharing one port. Totally normal. A website serves thousands of visitors through one port this way.

Idea 2: claiming a port and sharing a port are different actions

Linux asks a different question for each.

A new listener wants port P
Claim (bind)
"Is any other socket holding port P?"
Yes: refuse, error 98No: allow
A router connects to an existing listener
Share (accept)
"Is this a new caller?"
Yes: allow, same port, its own connection

Idea 3: parents and children

  1. The listener is the parent. It owns port P.
  2. Each connection it accepts is a child. A child shares its parent's port.
  3. If the parent goes away and a child stays, that child is an orphan. It still holds port P, but belongs to no listener.

Children may share their parent's port. A new, unrelated listener may not claim a port while any other socket still holds it.

Before and after the fix

Before: blocked

  • port P
    • old listener: closed
    • connection to Router B (orphan)
New listener: "Can I have port P?"
Linux: "No. Something still holds it." Error 98.

After: working

  • port P
    • new listener (the owner)
      • connection to Router A
      • connection to Router B
Both connections are children of the current listener, so sharing port P is allowed. No error.

So, the answer to the puzzle

  1. Before: a new listener asked to claim port P. Linux found Router B's orphan connection still on it, not a child of this new listener, and refused.
  2. After the restart: Linux had closed every old socket, so port P was empty. The new listener claimed it with no problem.
  3. Then Router A and Router B connected. Linux only had to share the port with children of the current listener, which is always allowed.

Same port, same IP. What changed was who owned it.

Why Linux has this rule

To protect connections. If a new program could grab a port while old connections still live on it, messages meant for the old connection could reach the wrong program. So Linux waits until the port is really free, unless the program explicitly asks to share.

For the technically curious
  • Why the orphan could exist: STY 2 in /proc/net/sctp means TCP-style SCTP (one-to-one). Every accepted connection gets its own socket, separate from the listener. So a connection can outlive its listener.
  • SO_REUSEADDR is a socket option that says "let me bind even if old connections still exist on this port." The Diameter stack apparently doesn't set it. With it, the start would likely have worked, but the orphan would still be there with Router B sending into it.
  • Not just SCTP: a TCP server that closes its listener while an accepted connection is still open hits the same error 98 on the next listen, without SO_REUSEADDR.
  • The four-value picture is a simplification. With multi-homing, SCTP uses sets of addresses on each side, but the idea is the same.

7The fix, and why it worked

The options

OptionResult
Start the service again, or a newer versionFails The blocker isn't in the service.
Ask the router side to reset Router B's connectionMaybe The process still holds the socket, so the port could stay taken.
Close that one connection inside the live process with a debuggerToo risky Could crash the process or break other connections.
Move the service to another portNo traffic The routers send to port P.
Restart the whole server processGuaranteed Linux closes every socket of a process when it ends.

The fix, step by step

  1. Force-stop the processLinux closes all its sockets, including the orphan.
  2. Port P is freeNothing holds it any more.
  3. Start the process and the serviceA fresh process. The new SCTP listener claims port P.
  4. Routers reconnectThey were retrying every few seconds. A and B each get a new connection.

Why it worked: asking vs forcing

Stop the serviceStop the process
Who cleans up connections?The application's own codeLinux
Can it forget one?Yes. That's what happenedNo, never
HereRouter B's connection left openEverything closed, port free

A stop asks the application to clean up. A process exit makes Linux clean up. The application forgot one connection. Linux doesn't forget.

  1. Why a forced stop? The vendor's documentation covers this exact case: with a Diameter SCTP connection open, a normal stop may not finish cleanly. The documented way is a forced stop, then a start.
  2. What got restarted? Only that one server process. The other services inside it blinked for a moment. Other programs on the machine kept running.

How I confirmed it

  • The server runs under a new process ID. The old process is gone.
  • Linux shows a listener on port P again.
  • Linux shows two connections on port P, one per router, both established.
  • Every connection has a new ID number. No leftovers.
  • The flood of rejected messages in the logs stopped.
The healthy state, in Linux's own words
$ cat /proc/net/sctp/eps      (trimmed)
 SST  LPORT  INODE      LADDRS
 10   P      108368138  192.0.2.10              <- listener back (10 = listening)

$ cat /proc/net/sctp/assocs   (trimmed)

 3   108364601  P      17921  *198.51.100.11 198.51.100.12   <- Router A
  • New inode numbers (108364601/2 instead of 432560) prove these are brand-new sockets.
  • The Diameter stack also bumped its Origin-State-Id, a counter a Diameter node raises on every restart. It tells the routers: "I restarted, old sessions with me are gone."

8A side lesson: the evidence almost disappeared

The server keeps its logs in 10 rotating files. When one fills up, the oldest gets deleted. Normally that covers days. During this incident, the "rejected message" errors were landing at hundreds of lines per second.

~14 s~14 s~14 s~14 s~14 s~14 s~14 s~14 s~14 s~14 s

10 files, about 14 seconds each: only the last ~2 minutes survived

By the time I looked, the logs from the moment the service stopped, and from the first failed starts, were already gone.

Copy the logs the moment an incident starts. An error flood can wipe the evidence in minutes.

A one-line snapshot command
tar czf ~/incident-$(date +%F-%H%M).tgz /path/to/logs/

9Takeaways

  1. "In use" doesn't mean "someone is listening"Check for leftover connections too, not just listeners.
  2. A stop is a request. A process exit is a guarantee.If an app won't release a socket, restarting its process will.
  3. Trust what Linux seesAfter a stop, look at Linux's own view. No listener but live connections on the port means an orphan.
  4. Inode, then fd, then processThis lookup finds the owner of any socket on Linux.
  5. Plan the stopAsk the peers to drop their connections first, or plan a process restart from the start.
  6. Save the logs firstThen start digging.
